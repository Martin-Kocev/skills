# Atlas data schema

`data/atlas.json` is the single source of truth. The UI renders it; it contains no presentation logic. `data/atlas.bundle.js` is a generated `window.__ATLAS__ = {…}` mirror so the atlas also opens over `file://` — never edit it by hand; `scripts/validate-atlas.mjs` regenerates it.

Machine-readable version: `templates/data/atlas.schema.json`. Worked example: `templates/data/atlas.json`.

## Shared building blocks

Used by nearly every item.

```jsonc
"id": "workflow-place-order",     // stable, permanent, kebab-case, prefixed by kind
"confidence": "verified",          // verified | inferred | unknown
"origin": "generated",             // generated | curated | inferred
"sources": [
  { "path": "src/orders/place.ts", "symbol": "placeOrder", "lines": [42, 71],
    "kind": "code", "note": "entry point" }
],                                 // kind: code | test | config | doc | migration | schema | script | commit
"depth": {
  "simple":   "Plain language, one analogy if it helps. 2–4 sentences.",
  "balanced": "Accurate architecture with real names and paths. 2–4 sentences. THE DEFAULT.",
  "deep":     "Implementation detail, edge cases, invariants, tests. May include one short excerpt."
},
"why": [
  { "q": "Why not call the database directly?",
    "a": "Every write also emits an audit row; the repository layer is the only place that guarantees both happen in one transaction.",
    "confidence": "verified",
    "sources": [{ "path": "src/db/repository.ts", "symbol": "withAudit", "kind": "code" }] }
],
"changed": { "state": "updated", "commit": "a1b2c3d", "note": "Step 4 now emits an event" },
                                   // state: new | updated | unchanged | removed
"conflict": { "claim": "README says uploads are synchronous",
              "reality": "src/upload/queue.ts enqueues them",
              "sources": [...], "assessment": "README predates the queue (inferred)" },
"contentHash": "…"                 // generated by validate-atlas.mjs — do not hand-write
```

`id` rules: permanent once published, kind-prefixed (`component-`, `workflow-`, `step-`, `entity-`, `channel-`, `subsystem-`, `term-`, `playbook-`, `check-`, `section-`), unique atlas-wide. See `references/progress.md`.

## repository

Every field is required. Produced by `scripts/git-metadata.mjs`.

```jsonc
{
  "name": "example-project",
  "path": "/abs/path/to/example-project",
  "remote": "github.com/acme/example-project",   // host+path only, never credentials; null if none
  "branch": "develop",                            // null when detached
  "tag": "v2.4.0",                                // null when not exactly on a tag
  "detached": false,
  "commit": "a1b2c3d4e5f6…",
  "commitShort": "a1b2c3d",
  "commitSubject": "Add reservation conflict handling",
  "commitTimestamp": "2026-07-30T11:14:02+02:00",
  "rootCommit": "0f0f0f0…",                       // identity check for update mode
  "generatedAt": "2026-07-31T09:20:11+02:00",
  "workingTreeClean": false,
  "dirtyFiles": [ { "path": "src/orders/place.ts", "status": "modified" } ],
  "lastValidatedAt": "2026-07-31T09:31:44+02:00",
  "atlasLocation": "sibling",                     // sibling | inside-repo | custom
  "gitExcludeApplied": false                      // true only in the inside-repo fallback
}
```

**Display rules the UI must honour:**

- Always visible: `Atlas updated through commit a1b2c3d — "Add reservation conflict handling"`
- Repo ahead of recorded commit → non-disruptive banner: `This atlas may be outdated. The repository is 14 commits ahead of the version currently documented.` A quiet strip, not a modal.
- `workingTreeClean: false` → separate notice listing `dirtyFiles`, worded so uncommitted work is never presented as part of a stable version: `Generated while 3 files had uncommitted changes. Everything below describes committed HEAD.`
- `detached: true` → show the commit, not a branch name.

## meta

```jsonc
{
  "title": "Example Project Codebase Atlas",
  "oneLiner": "A restaurant booking system: guests reserve tables, staff manage them from an admin console.",
  "hook": "Two people can tap 'Reserve' on the same table at the same moment. Most of this system exists to make sure only one of them wins.",
  "primaryLanguages": ["TypeScript", "SQL"],
  "stack": ["Next.js", "Postgres", "Redis"],
  "sizeSignals": { "files": 412, "trackedLines": 38100 },   // optional, understated
  "scopeNote": "v1 covers reservations, auth, and the admin console. Billing is not yet documented."
}
```

`hook` is the first thing a reader sees. It must be true, specific to this repository, and answerable by the atlas.

## components

Use `components` as the canonical island/module collection. Do not create a second disconnected architecture model for the visual world. Friendly names, technical names, hierarchy, map positions, route endpoints, search results, progress, and the accessible list/tree all point to the same stable IDs.

```jsonc
{
  "id": "component-api",
  "name": "Reservations API",
  "technicalName": "@example/reservations-api",
  "worldType": "island",             // island | module
  "parentId": null,                   // parent component id for a nested module
  "category": "backend",
  // frontend | admin | mobile | backend | api | worker | domain | shared-lib | shared-ui
  // | database | cache | storage | queue | events | external | infra | build | tests | cli
  "responsibility": "Accepts reservation requests and enforces table availability.",
  "audience": "Guest web app, admin console",
  "entryPoint": { "path": "src/api/server.ts", "symbol": "createServer" },
  "keyDirectories": ["src/api/routes", "src/api/middleware"],
  "example": "POST /api/reservations with a table id and time window returns 409 when the slot is taken.",
  "tests": [{ "path": "test/api/reservations.spec.ts", "kind": "test" }],
  "depth": { … }, "why": [ … ], "sources": [ … ],
  "confidence": "verified", "changed": { … },
  "layer": 2,            // 0 = clients … n = infrastructure; drives map layout
  "accent": "amber",     // optional palette slot; category shape/icon must also distinguish it
  "map": {
    "x": 0.42, "y": 0.31,             // normalized, deterministic, preserved across updates
    "layoutKey": "layer-2:api",        // stable input to placement; never random per render
    "theme": "harbor"
  },
  "owners": ["Platform team"],        // only when repository evidence supports ownership
  "complexity": "medium",             // low | medium | high; explain the basis in depth/sources
  "risk": "medium",
  "health": "passing",
  "lastChangedCommit": "a1b2c3d"
}
```

Aim for 5–12 top-level islands. More than ~15 turns the world map into a hairball—group smaller pieces as modules/areas. Derive initial coordinates from stable IDs, layer, and relationship grouping. Reuse published coordinates byte-for-byte unless a meaningful architecture change requires movement; record such movement in the related change group.

`map`, `worldType`, `layoutKey`, `accent`, and `routeType` are **excluded from `contentHash`** by `validate-atlas.mjs`. They describe how a thing is drawn, not what the atlas claims about the repository — so re-placing or re-theming the world never tells readers that a section changed. Fields that *are* claims (`runtime`, `strength`, `relationshipType`, `direction`) stay inside the hash. If you add a presentation-only field, add it to `HASH_EXCLUDE` in the same commit.

## connections

Edges of the architecture map and the substance of the communication section.

```jsonc
{
  "id": "channel-api-db",
  "from": "component-api", "to": "component-db",
  "mechanism": "sql",
  // http | rpc | graphql | server-action | websocket | sse | queue | event-bus | webhook
  // | scheduled | polling | shared-storage | ipc | sql | cache | import
  "label": "reads and writes reservations",
  "routeType": "cable",              // sea-route | current | bridge | ferry | cargo | cable | air | broken
  "relationshipType": "infrastructure-dependency",
  "runtime": true,                    // true runtime flow | false static relationship
  "strength": "tight",               // weak | normal | tight
  "data": "Reservation rows and the availability lock",
  "direction": "one-way",          // one-way | two-way
  "validation": "Zod schema at the route boundary, CHECK constraints in the table",
  "auth": "Session cookie verified in middleware before the handler runs",
  "onSuccess": "Row committed, `reservation.created` published",
  "onFailure": "Unique constraint violation surfaces as HTTP 409 with a retry hint",
  "retry": "None — the client re-requests availability instead",
  "recovery": "Client refetches the slot list on 409",
  "whyThisMechanism": "A database constraint is the only place both racing requests meet.",
  "confidence": "verified", "sources": [ … ], "changed": { … }
}
```

Treat route appearance as a redundant visual encoding, never as the claim itself. The semantic list must state endpoints, direction, mechanism, runtime/static nature, explanation, confidence, and sources. Filter route categories independently and show only critical or selected routes by default.

## workflows

The highest-value content in the atlas. Each is a story with an arc.

```jsonc
{
  "id": "workflow-place-reservation",
  "title": "A guest reserves a table",
  "hook": "This is where a tap on a button becomes a row nobody else can take.",
  "trigger": "Guest presses Reserve in the booking form",
  "outcome": "A confirmed reservation and an updated availability grid",
  "recap": "The UI is optimistic, the API is authoritative, and the database is the referee.",
  "steps": [
    {
      "id": "step-place-reservation-1",
      "title": "The form submits",
      "layer": "frontend",
      // frontend | request | route | middleware | service | domain | data | external
      // | event | job | response | ui-update
      "plain": "The booking form disables itself and sends the chosen table and time to the API.",
      "source": { "path": "app/book/BookingForm.tsx", "symbol": "onSubmit", "lines": [88, 104] },
      "why": "Disabling first prevents a double submission from the same guest.",
      "input": "Table id, start time, party size",
      "output": "POST /api/reservations",
      "failure": "Offline or 5xx → inline error, form re-enabled, nothing was written",
      "test": { "path": "test/e2e/booking.spec.ts", "symbol": "double submit" },
      "excerpt": { "lang": "tsx", "caption": "The guard that prevents a double POST",
                   "code": "if (pending) return;\nsetPending(true);" },
      "changed": { … }, "confidence": "verified"
    }
  ],
  "failureScenario": { "title": "Two guests, one table",
                       "steps": ["…"], "resolution": "The second request receives 409." },
  "confidence": "verified", "sources": [ … ], "changed": { … }
}
```

5–12 steps is the sweet spot. Fewer skips the interesting part; more loses the thread. Always include the return path — the reader wants to see the UI update.

## channels

Narrative layer over `connections` — one entry per *mechanism*, not per edge. Groups the connections that use it, and carries the success and failure scenarios.

```jsonc
{ "id": "channel-websocket", "mechanism": "websocket",
  "title": "Live table updates", "connectionIds": ["…"],
  "initiator": "…", "receiver": "…",
  "successScenario": { "title": "…", "steps": ["…"] },
  "failureScenario":  { "title": "Socket drops mid-service",
                        "steps": ["…"], "recovery": "Client refetches on reconnect" },
  "depth": { … }, "why": [ … ], "sources": [ … ], "confidence": "…" }
```

Include at least one success and one failure scenario per mechanism the repository supports.

## explorer

Use `explorer` for the levels below a top-level island. Keep conceptual groups primary and retain the real filesystem as a disclosed parallel tree.

```jsonc
{

               "technicalName": "Domain logic", "kind": "area",
               "what": "The rules that would still be true if the UI were replaced.",
               "paths": ["src/availability", "src/orders"],
               "componentIds": ["component-domain"],
               "parentId": "component-domain", "keyFileIds": ["file-place-order"] }],
  "files": [{ "id": "file-place-order", "kind": "file", "name": "place.ts",
              "path": "src/orders/place.ts", "parentId": "area-domain-rules",
              "responsibility": "Coordinates reservation placement.",
              "symbols": ["placeOrder"], "dependencies": ["file-reservation-repo"],
              "dependents": ["file-reservation-route"], "tests": [ … ],
              "whyItMatters": "This is the transaction boundary for the workflow.",
              "sources": [ … ], "confidence": "verified", "changed": { … } }],
  "views": ["conceptual", "folders", "recently-changed", "current-workflow", "feature", "unexplored"],
  "tree": [{ "path": "src", "kind": "dir", "children": [ … ] }],   // 2–3 levels only
```

Require stable IDs for modules, areas, and selected files. A file move updates `path` without changing its ID when responsibility remains the same. Map/list/tree selection, search, bookmarks, tours, quests, progress, and Recent Changes must reference these same IDs.

## readingOrder

A directed acyclic graph of the files to read, in an order where every one is explained by the ones before it. See `references/sections.md` §3b for the authoring rules.

```jsonc
{
  "id": "section-reading-order",
  "hook": "Forty-five files, in the order that makes each one explain the next.",
  "goal": "What the reader can do once they have been through the whole graph.",
  "stages": [
    { "id": "stage-orient", "name": "Get your bearings",
      "what": "Why these files belong together and what the stage buys the reader." }
  ],
  "nodes": [{
    "id": "read-place-order",              // permanent, prefixed "read-"
    "stage": "stage-domain",
    "title": "place.ts",                   // usually the bare file name; the node is small
    "path": "src/orders/place.ts",         // validated against repository.commit
    "what": "The transaction boundary for placing a reservation.",
    "lookFor": "That the overlap constraint — not the service — is what decides a conflict.",
    "validate": "`test/api/reservations.spec.ts` proves it; the double-booking case is the one to read.",
    "dependsOn": ["read-reservation-entity", "read-repository"],
    "fileId": "file-place-order",          // optional: link into the explorer
    "componentId": "component-api",        // optional: link into the world map
    "sources": [ … ], "confidence": "verified", "changed": { … }
  }]
}
```

**The ordering invariant.** Every `dependsOn` target must be earlier: an earlier stage, or an earlier index within the same stage. That makes the graph acyclic and makes the drawn layout (stage = row, authored index = column) correct by construction. `validate-atlas.mjs` enforces it; a violation is an error, not a warning.

Node ids are progress items under the ordinary store and the ordinary permanence rule, but they are **excluded from the section-progress denominator** — see `references/progress.md`.

## Recent change groups

Represent each conceptual change group as a `learningPaths` item with `kind: "what-changed"`. This keeps its stable ID inside the existing machine-validated collection. Do not add a disconnected raw commit feed.

```jsonc
[{ "id": "path-change-reservation-conflicts", "kind": "what-changed",
   "title": "Reservation conflicts now resolve at the database boundary",
   "blurb": "Review the conflict behavior and its affected route.",
   "stepIds": ["workflow-place-reservation", "component-api"],
   "commits": ["a1b2c3d4…"],
   "summary": "The API maps overlap violations to a conflict response.",
   "why": "Commit message states that concurrent requests previously surfaced as 500s.",
   "affectedIds": ["component-api", "workflow-place-reservation", "file-place-order"],
   "files": ["src/orders/place.ts", "test/api/reservations.spec.ts"],
   "risk": "medium", "tests": [ … ], "documentationImpact": "README response table updated",
   "reviewOrder": 1, "confidence": "verified", "sources": [ … ] }]
```

Keep the `path-change-*` ID stable for the same conceptual group across atlas refreshes. Progress stores whether the reader reviewed the group; atlas data never stores personal review state. Explain concepts before linking to raw diffs.

## openQuestions

Honesty, surfaced. Reads better than a fake answer and tells the reader where to look.

```jsonc
[{ "id": "question-retry-policy", "question": "Why is the email retry limit 3?",
   "whatIsKnown": "`src/mail/send.ts` retries three times with backoff.",
   "whyUnknown": "No comment, test, or commit message explains the number.",
   "whereToLook": "The team, or the provider's rate-limit docs." }]
```

## learningPaths

Assembled last, from sections that exist. Only offer a path the repository supports.

```jsonc
[{ "id": "path-quick-overview", "kind": "quick-overview",
   "title": "Quick overview", "blurb": "The whole system, one idea at a time.",
   "stepIds": ["section-overview", "component-web", "component-api", "entity-reservation",
               "workflow-place-reservation", "section-delivery"] }]
```

Kinds: `quick-overview`, `follow-one-action`, `explore`, `continue`, `what-changed`, `review-unfinished`, `reading-order`. Show **step counts, never time estimates.** A `reading-order` path is a jump into the reading-order graph rather than a list of stops; its `stepIds` are the graph's nodes.

## Quest presentation

Build Quests as a presentation over existing `learningPaths` and `knowledgeChecks`, both of which already have stable, machine-validated IDs. Do not create a parallel quest collection.

```jsonc
{ "pathId": "path-follow-login",
  "checkIds": ["check-login-enforcement"],
  "goal": "Follow identity from the sign-in form to backend enforcement.",
  "completionMessage": "You can now identify where authentication becomes authorization." }
```

Derive completion locally from the referenced stable IDs. Never add scores, timers, streaks, ranks, losses, punishment, manipulative notifications, or locked core content.
